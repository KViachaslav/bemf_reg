# _uart_test — тестовая прошивка проверки UART

Автономная (bare-metal, без HAL) прошивка, чтобы **до подключения мотора**
проверить только линию UART: `STM32F103 (PA9/PA10) <-> USB-UART (CH340) <-> ПК`.

Не входит в основную сборку проекта (папка `_uart_test/`) и никак не влияет
на боевую прошивку `Core/`.

## Что делает

| Пин | Функция в тесте |
|---|---|
| PA9  | `USART1_TX` — баннер при старте + `PING n  uptime=... ms` каждые 500 мс |
| PA10 | `USART1_RX` — **эхо**: каждый принятый байт отправляется обратно |
| PC13 | LED (active low) — мигает ~1 Гц (признак, что МК жив) |
| PA8  | **принудительно низкий** — затвор IRLZ44N, ключ гарантированно закрыт |

Тактирование: `HSI 8 МГц / 2 × 16 = 64 МГц` (как в боевой прошивке),
поэтому скорость 115200 совпадает с рабочей конфигурацией.

## Сборка

```powershell
powershell -ExecutionPolicy Bypass -File _uart_test\build_test.ps1
```

Результат: `_uart_test\build\uart_test.elf` (+ `.bin`, `.map`).
Компилятор берётся из состава установленной STM32CubeIDE (см. скрипт).

## Прошивка (ST-Link по SWD)

```powershell
powershell -ExecutionPolicy Bypass -File _uart_test\flash_test.ps1
```

Или вручную:

```
STM32_Programmer_CLI -c port=SWD -w _uart_test\build\uart_test.elf -v -rst
```

## Подключение и проверка

1. USB-UART (CH340) ⇄ Blue Pill:
   - `PA9`  (TX, MCU) → `RXD` адаптера
   - `PA10` (RX, MCU) ← `TXD` адаптера
   - `GND` ⇄ `GND` (обязательно!)
2. Открыть терминал: **115200, 8N1, без flow control** (PuTTY / Tera Term /
   Arduino IDE Serial Monitor).
3. Сразу после сброса должно появиться:

```
=== BEMF_reg UART TEST ===
USART1 PA9(TX)/PA10(RX) 115200 8N1, SYSCLK=64MHz (HSI/2 x16)
Echo mode: everything you type is sent back.
LED PC13 blinks ~1Hz.

PING 0  uptime=0 ms  [PA9->CH340->PC]
PING 1  uptime=500 ms  [PA9->CH340->PC]
...
```

4. Наберите любой текст — он должен вернуться эхом (проверка RX).
5. LED на плате должен мигать ~1 Гц (проверка, что прошивка исполняется).

### Диагностика

| Симптом | Причина |
|---|---|
| Нет вывода, LED не мигает | нет питания / прошивка не залита / плата удерживается в reset |
| LED мигает, но текста нет | не тот COM-порт; скорость не 115200; TX/RX не перекрёстно; нет общего GND; не установлен драйвер CH340 |
| Текст «крякозябры» | неверная скорость/формат линии |
| В RX эхо не возвращается, TX идёт | перепутаны PA10 (RX) ↔ адаптер TXD или неверный GND |
| В списке портов нет CH340 | адаптер не подключён / драйвер не установлен |

## Результат проверки на этой плате (подтверждено)

Плата: самодельная, STM32F103C8T6, **без светодиода**, питание от ST-Link (3.28 В).
USB-UART: CH340 в отдельном USB-порту, в системе виден как
`Устройство с последовательным интерфейсом USB (COM11)` (generic-имя, не «CH340»).

Захват `read_uart.ps1 -Port COM11 -Seconds 12 -LineTime -Reset -Send -SendText HELLO123 -SendGapMs 120`:

```
[+    0 ms] >>> RESET МК через ST-Link
[+   42 ms] P53  uptime=26500 ms  [PA9->CH340->PC]   <- буфер драйвера (порт был закрыт)
[+  287 ms] 
[+  290 ms] === BEMF_reg UART TEST ===
[+  294 ms] USART1 PA9(TX)/PA10(RX) 115200 8N1, SYSCLK=64MHz (HSI/2 x16)
[+  298 ms] Echo mode: everything you type is sent back.
[+  300 ms] LED PC13 blinks ~1Hz.
[+  306 ms] PING 0  uptime=0 ms  [PA9->CH340->PC]
[+  806 ms] PING 1  uptime=500 ms  [PA9->CH340->PC]
[+ 1311 ms] PING 2  uptime=1000 ms  [PA9->CH340->PC]
...
[+ 4289 ms] >>> ОТПРАВЛЕНО: HELLO123
[+ 4292 ms] HELPING 6  uptime=3000 ms  [PA9->CH340->PC]   <- HEL + PING 6
[+ 4295 ms] LO12PING 7  uptime=3500 ms  [PA9->CH340->PC] <- LO12 + PING 7
[+ 4297 ms] 3
```

Выводы:

| Что | Результат |
|---|---|
| Тактирование (HSI/2 ×16 = 64 МГц) | OK — период `PING` ≈ 505 мс |
| TX: PA9 → CH340 → ПК | OK — баннер + поток `PING`, без «крякозябр» |
| RX: CH340 → PA10 | OK — вся строка `HELLO123` вернулась эхом |
| Сброс через ST-Link | OK — `-rst` работает, ловится стартовый баннер |

Замечания:

- Тестовый приём сделан **по опросу** раз в ~1 мс, а у STM32F1 в USART нет FIFO:
  сплошной пакет (`-Send` без `-SendGapMs`) вызовет overrun и в эхо дойдёт
  только первый байт. Это ограничение теста, **не аппаратной части**.
- Боевая прошивка принимает иначе — через `HAL_UART_Receive_IT()` плюс
  `HAL_UART_ErrorCallback()` с очисткой ORE/FE/NE/PE (`Core/Src/uart_cmd.c`),
  поэтому поток с ПК она обработает нормально.

## Проверка вывода прямо с ПК (без стороннего терминала)

Готовый скрипт `_uart_test\read_uart.ps1` сам находит порт (Bluetooth-порты
COM3–COM8 игнорируются) и читает UART в 115200 8N1:

```powershell
# просто прочитать вывод (авто-поиск порта, Bluetooth игнорируются)
powershell -ExecutionPolicy Bypass -File _uart_test\read_uart.ps1 -Seconds 8

# с метками времени: сразу видно, живой эфир или буфер драйвера
powershell -ExecutionPolicy Bypass -File _uart_test\read_uart.ps1 -Port COM11 -Seconds 12 -LineTime

# поймать стартовый баннер: сбросить МК через ST-Link уже после открытия порта
powershell -ExecutionPolicy Bypass -File _uart_test\read_uart.ps1 -Port COM11 -Reset -LineTime

# проверить RX: отправить строку и увидеть эхо
#   -SendGapMs 120 -> слать по символу с паузой (тестовый приём идёт по опросу,
#   у STM32F1 в USART нет FIFO -> сплошной поток даёт overrun и теряет байты)
powershell -ExecutionPolicy Bypass -File _uart_test\read_uart.ps1 -Port COM11 -Send -SendText HELLO123 -SendGapMs 120 -LineTime

# прогон мотора боевой прошивки: уставка -> R -> периодический '?' -> стоп X
#   ('?' нужен потому, что молчание ПК > 5 с при работающем моторе = FAULT_UART_LOST)
powershell -ExecutionPolicy Bypass -File _uart_test\read_uart.ps1 -Port COM11 -Seconds 18 -LineTime `
  -TimedCmds '1000:S300;1600:R;5000:?;8500:?;12000:?;16000:X'
```

Скрипт печатает принятое построчно и в HEX — удобно ловить «крякозябры»
при неверной скорости.

### Ключевые параметры `read_uart.ps1`

| Параметр | Что делает |
|---|---|
| `-Port COM11` | явный порт (иначе авто-выбор первого не-Bluetooth) |
| `-Seconds N` | длительность захвата |
| `-LineTime` | метка `[+ N ms]` у каждой строки |
| `-Reset` | `STM32_Programmer_CLI -c port=SWD -rst` после открытия порта |
| `-Send` / `-SendText` | отправить строку (по умолчанию `HELLO`) |
| `-TimedCmds "1000:S300;1600:R;5000:?;9000:X"` | расписание команд `"<мс>:<текст>;..."` — каждая уходит в свой момент. Нужно для прогонов мотора: уставка + `R`, затем периодический `?` (иначе `FAULT_UART_LOST` заглушит мотор через 5 с молчания ПК) и `X` — всё в одном захвате |
| `-SendGapMs N` | слать по символу с паузой N мс (`0` = сплошным пакетом) |
| `-WaitSec N` | ждать появления USB-UART порта до N секунд |

### Важно про буфер драйвера

При открытии порта первыми приходят данные, накопившиеся в драйвере, **пока
порт был закрыт** (может быть старый `PING ... uptime=<большой>`). Именно
поэтому включайте `-LineTime`: живой эфир имеет метку ≈ `uptime`, а старьё —
большой `uptime` при метке `[+ 0 ms]`.

### Авто-выбор порта (исправлено)

Результат `Get-CandidatePorts` разворачивается через `@(...)`: при **единственном**
подходящем порте PowerShell «схлопывает» массив в строку, и `$cand[0]` вернул бы
символ `C` вместо `COM11` (ошибка выглядела как «Доступ к порту 'C' закрыт»).
Плюс результат проверяется по шаблону `^COM\d+$`, и при несовпадении скрипт
печатает подсказку задать порт явно (`-Port COM11`).

## Пульт оператора в браузере (`motor_control.html`)

Вместо консольного захвата мотором можно управлять из браузера: страница
`_uart_test\motor_control.html` работает через **Web Serial API** (Chrome/Edge 89+),
сама держит keep-alive `?` и рисует телеметрию в реальном времени.

```powershell
# вариант 0 (без сервера): просто открыть _uart_test\motor_control.html двойным щелчком
#   Chrome/Edge считают локальные файлы доверенным контекстом -> Web Serial доступен

# вариант 1: поднять localhost-сервер и открыть пульт в Chrome/Edge
powershell -ExecutionPolicy Bypass -File _uart_test\serve_motor_control.ps1

# другой порт / без автооткрытия браузера
powershell -ExecutionPolicy Bypass -File _uart_test\serve_motor_control.ps1 -Port 8100 -NoBrowser
```

Почему через сервер: Web Serial обязан работать в **защищённом контексте**
(secure context). Chrome/Edge считают доверенными не только `https` и
`http://localhost`, но и **локальные файлы** — поэтому пульт можно открыть просто
двойным щелчком по `motor_control.html` (проверено: работает из `file://`).
Сервер — это удобство, а не требование:

- стабильный адрес `http://localhost:8099/` (можно обновлять страницу, держать
  закладку, открывать в разных окнах);
- браузер поднимается сам, файл не нужно искать в проводнике;
- одинаковое поведение во всех версиях браузеров (в старых сборках `file://`
  доверенным не считался, и `navigator.serial` там отсутствовал).

Сервер слушает только `localhost`, отдаёт каталог `_uart_test\` и останавливается
по `Ctrl+C`. Если пульт открыт из файла, а в журнале написано
«Web Serial API недоступен» — значит у вас как раз старый браузер, используйте
`serve_motor_control.ps1`.

| Элемент пульта | Что отправляет / показывает |
|---|---|
| «Подключить порт» | `navigator.serial.requestPort()` — выбор COM-порта в диалоге браузера, открытие 115200 8N1 (VID/PID показываются в журнале) |
| «▶ Пуск (R)» / «■ Стоп (X)» | команды `R` / `X`; `Esc` — аварийный `X` в любой момент |
| уставка + пресеты 0…3000 | `S<rpm>` (пресет отправляет уставку сразу, без пуска) |
| Kp / Ki | `K<kp>,<ki>` |
| «C — шаг 1» / «C&lt;rpm&gt; — шаг 2» | калибровка `K_motor` (шаг 1 — с подтверждением: мотор 1 с на 50 % ШИМ) |
| плитки RPM/SET/DUTY/ERR/ADC/VS/FLT | разбор кадров 10 Гц по тому же формату, что в `uart_cmd.c`; `FLT≠0` подсвечивается красным и попадает в журнал отдельным событием |
| график | RPM (сплошная) и уставка (пунктир), окно 60 с, обновление на каждом кадре |
| «Сохранить лог» | `motor_ui_<дата>_<время>.txt` — все строки с временем: `>>` команды ПК, `<-` ответы платы, `==` события пульта (годится как протокол испытаний) |
| «Любая команда» | отправка произвольной строки (`C1715`, `K2,0.5`, `?`, …) — удобно для нестандартных прогонов |

Тонкости, заложенные в пульт:

- **keep-alive обязателен:** молчание ПК > 5 с при работающем моторе = `FLT=3`
  (`FAULT_UART_LOST`). Пульт шлёт `?` каждые 2 с (настраивается 0.3…4 с) и делает
  паузу 0.8 с после команд пользователя — прошивка разбирает строки однопоточно
  (`uart_cmd_on_byte`: `if (line_ready) return;` отбрасывает байты, пока не
  разобрана предыдущая строка), поэтому «вклинившийся» keep-alive мог бы съесть
  команду.
- при нажатии «Отключить» пульт по умолчанию сначала шлёт `X` (галочка
  «слать X при отключении»). Если вкладку просто закрыть при работающем моторе,
  мотор остановит сама прошивка через 5 с (`FLT=3`) — это штатная защита, а не сбой.
- «Сохранить лог» пишет **все** кадры, а окно журнала — только события; кадры
  можно включить галочкой (показывается каждый 10-й, чтобы не забивать экран).
- пульт и `read_uart.ps1` **не работают одновременно**: COM-порт занимает только
  один процесс, второй получит «порт занят» (в пульте это разбирается отдельным баннером).

## Захваты боевой прошивки на стенде (12 В + мотор)

Скрипт тот же — меняется только прошивка в МК и набор команд (`-TimedCmds`).

| Лог | Что проверено |
|---|---|
| `motor_base.txt`, `motor_r0.txt` | первый пуск до правок: `R` → `OK RUN`, но сразу `FLT=2` при валидных кодах АЦП — так была найдена ошибка типа буфера DMA (см. §16 README проекта) |
| `motor_r1.txt` | после правки: `R` при `SET=0` → `OK RUN`, `DUTY=5.0%`, `ADC=2492` (≈12.05 В на низкой стороне), `VS=12.1V`, `FLT=0` |
| `motor_s300b.txt` | замкнутый контур после правки анти-виндапа: ШИМ 5.2 → 17.3 %, `RPM` 5 → 150 при `ERR≈150`, `X` → `OK STOP`, `FLT=0` |
| `motor_s1500.txt` | `S1500`: ШИМ 5 → 29 %, далее плато на пределе `Ki·PID_INTEGRAL_MAX`, мотор крутится устойчиво |
| `motor_stress.txt` | финальные настройки (`K_motor=330`, `Kp=1.5`, `Ki=0.6`, `I_MAX=12000`): `S300` → 280 об/мин в мёртвой зоне (ШИМ 11.5 %), ступень `S1500` → плавно 773 → 1251 без перерегулирования, ступень `S2000` → 1881 об/мин при ШИМ 52 %, `VS=12.1V`, `FLT=0` |
| `motor_t1.txt`, `motor_t2.txt`, `motor_t3.txt` | подбор `Kp`/`Ki` при `S1500`: `Kp=1.0` — медленно, `Kp=2.5` — раскачка оборотов, `Kp=1.5, Ki=0.6` — плавно и быстро (выбрано) |
| `motor_k333.txt` | калибровка по паспорту мотора: `C` → `VBEMF=5.201 В`, `C1715` → `OK K=329.7` |
| `motor_cal1.txt` | `C` при лимите тока БП 1 А → `ERR FAULT DURING CAL`, `FLT=4` — реальная просадка питания мотора до 4.55 В (пусковой ток выше лимита БП), прошивка сработала верно |
| `motor_cal2.txt` | `C` после подъёма лимита до 3 А → **`OK CAL VBEMF=5.144 V, SEND C<rpm>`**, `VS=12.1V`, `FLT=0`: шаги 3–4 чек-листа пройдены (50 % ШИМ, открытый цикл, без аварий) |
| `motor_flt3.txt` | `FLT=3` («потеря связи»): после `?` 5 с молчания → `FLT=3`, `DUTY=0.0%` (ШИМ снят), `X` → `OK STOP`, `FLT=0` |
| `motor_idle.txt`, `motor_final.txt` | штатное «чистое» состояние стенда: `SET=0 DUTY=0.0% ERR=0 FLT=0` |
| `rx_*.txt` | проверка команд `?`, `S`, `K`, `C`, `R`, `X`, `Z` (см. раздел выше) |

Порядок работы с мотором, который экономит нервы: сначала `X` (стоп + снятие аварии),
затем `S<rpm>`, затем `R`; в течение прогона держать паузу между командами < 5 с
(иначе защита `FAULT_UART_LOST` сама заглушит мотор), в конце — обязательно `X`.

## Сборка/прошивка не мешают основной прошивке

Папка `_uart_test/` не является source-folder проекта CubeIDE — файлы
основной прошивки (`Core/`) не затрагиваются. Чтобы вернуть боевую прошивку,
прошейте её ELF: `_build\out\BEMF_reg.elf` (собран `_build\build_main.ps1`) либо
`Debug/BEMF_reg.elf` из IDE.
